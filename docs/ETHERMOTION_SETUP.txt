UALR DEMO - ETHERMOTION DIVERTER SETUP

The conveyor is controlled by its own hardware. The demo uses MEASURED steady
belt speed to predict when a bottle reaches and clears the divert point. It
does not command or stop the belt and has no encoder, belt-run input, or
independent bottle/diverter position sensing.

0 PASS   -> no movement by default, or the selected PASS primary program.
1 REJECT -> the selected REJECT primary program.
An optional shared RETURN program can follow either selected primary program.
These are routing choices, not 0/1 degrees or raw electrical outputs. Your
saved EtherMotion moves determine travel, position, and motor direction.

1. PREPARE THE SAVED PROGRAMS

Open the installed EtherMotion application, normally:
%USERPROFILE%\Desktop\EtherMotion\EtherMotion.exe
Its local service normally uses http://127.0.0.1:8765. Keep it running.

Configure the actual driver's address, gearing/pulse scale, permitted speed,
acceleration, deceleration, and mechanism travel limits. Verify direction and
physical travel. There is no universal reject angle in this demo. For absolute
positions or a saved-zero return, establish the commissioned zero/reference.
EtherMotion does not automatically undo a move after interruption.

Choose one program arrangement:

A. Whole saved cycle, no separate RETURN program
   Save a primary Once cycle containing EXTEND/ROUTE, enough physical dwell,
   then RETURN to the intended clear state. The app cannot insert a dwell
   between steps inside that saved cycle. Its Hold control only delays later
   stages/repeats; it cannot extend the mechanism's dwell inside this program.

B. Primary and separate RETURN programs
   Save the REJECT primary movement as one Once program. Optionally save a
   PASS movement as another Once program. Save the common RETURN movement as
   a separate Once program. The demo waits for the primary to complete, then
   waits until BOTH predicted bottle clearance and primary-completion + Hold
   before requesting RETURN. Confirm that the shared return is physically
   correct after either primary. A blank PASS primary means no movement and
   never invokes RETURN on its own.

Every selected program must have Repeat = Once and valid saved driver actions.
The demo requests 1-10 sequential repeats itself; do not select Repeat or Until
stopped in EtherMotion. A Home step is not needed for every bottle. Establish
any required zero using the mechanism's commissioned procedure.

Test each program and the complete selected sequence deliberately in EtherMotion.
Confirm actual position, physical dwell, clearance, return, and total cycle
time before sending automatic bottle events. EtherMotion Stop is a network
deceleration request; it does not replace the machine's physical stop if the
PC, network, or drive communication fails.

2. PREPARE ETHERMOTION FOR PC EVENTS

Connect all drivers used by the selected PASS, REJECT, and RETURN programs.
Resolve alarms; require enabled, ready, configured, identity-verified, idle
status. Absolute/saved-zero moves require a valid zero/reference.

In PC events, enable Ethernet triggers on every participating driver. This is
the runtime remote_enabled gate. Saving a cycle does not enable it. Stops,
disconnects, and faults can disable it; inspect status after a fault.

The demo does not connect physical drivers, change motion modes, set zero,
enable Ethernet triggers, or install physical cycles automatically. Discovery
and readiness checks only read configuration/runtime; they do not move hardware.

3. CONNECT THE DEMO AND CHOOSE PROGRAMS

Under Diverter, enter http://127.0.0.1:8765 when both applications run on this
PC. Open EtherMotion opens the application; Discover / check connection reads
the service's saved Once programs and readiness.

Choose the REJECT primary program, optional PASS primary, and optional shared
RETURN program. Choose PASS/REJECT repeat counts from 1 to 10. Each program is
checked against its saved participants/readiness. Discovery uses /api/state
and keeps the local token in the backend; do not paste it into public logs.

Use a live USB/Basler source, select your bottle/color models under Models,
and verify classifications before enabling live output. Output is disarmed
at startup. Simulation and recorded video never send motion commands.

Bottle confidence and Color confidence under Models can be adjusted during inspection while
output is disarmed. Changes reset old tracks and require a fresh inference
result before arming. Recheck results after each adjustment; old bottle
identities and their decisions do not survive that change.

4. CALIBRATE ARRIVAL, MOVEMENT, AND CLEARANCE

Measure steady belt speed, decision-line-to-diverter distance, bottle length
along the belt, and the mechanism's move time. Speed is a measured calculation
input; this control does not set the conveyor motor speed.

With time expressed in seconds:

  travel = distance_mm / belt_speed_mm_s + delay_ms / 1000
  arrival_at = captured_at + travel
  due_at = arrival_at - lead_ms / 1000
  clearance_at = arrival_at + bottle_length_mm / belt_speed_mm_s
                           + clearance_ms / 1000

The capture timestamp belongs to the tracked decision-line event. The app
preserves these deadlines; it does not clamp an impossible trigger to now.
Arming requires lead_ms >= measured move_ms and travel >= lead_ms / 1000.
Use lead that covers measured command/communication and physical response.
The initial primary send deadline is the EARLIER of due_at + 250 ms and
arrival_at - move_ms / 1000. A missed initial window disarms output rather
than sending a stale first cycle. Later repeats and returns follow their
completion/hold sequence, not that first-bottle trigger deadline.

Example: 100 mm travel at 200 mm/s with no additional delay gives 500 ms to
arrival. A 200 ms lead requests the first primary at 300 ms. A 100 mm bottle
needs another 500 ms to pass the divert point; with a 100 ms clearance margin,
its predicted clearance is 600 ms after arrival, or 1100 ms after detection.

These times are calibrated estimates, not measured physical position. Verify
at low speed with representative bottles. Slip, a belt stall, changed speed,
geometry, or mechanism response invalidates a previous calibration.

5. HOLD, RETURN, REPEATS, AND BOTTLE SPACING

For a separate RETURN program, each repeat executes:

  PRIMARY request -> matching run completes
  wait until max(primary_completed_at + hold_ms / 1000, clearance_at)
  RETURN request -> matching run completes

Then the next repeat can start. There is no extra hold after the final return.
Hold is measured after primary completion, not after HTTP acceptance. The
clearance deadline still applies when Hold is zero or the primary finishes
before the bottle arrives. If the primary finishes late, its completion + Hold
may be later than predicted clearance.

With no separate RETURN, the primary saved cycle must perform its own physical
dwell/return. Between repeats the demo waits for primary completion, the hold,
and predicted bottle clearance before starting the next complete saved cycle.
A repeat means another whole programmed cycle for the same bottle event; it
does not create another detected bottle. Allow spacing for the entire sequence.

Spacing checks apply to ALL bottles, including PASS bottles whose own outcome
requests no movement. A PASS bottle can still arrive while another sequence
has the mechanism extended. Busy/overlapping events disarm output rather than
issuing a conflicting cycle. DISARMING CANNOT STOP THE CONVEYOR. It also cannot
prove that the mechanism is retracted. Manage physical bottle flow and resolve
the mechanism state before resuming.

6. ACCEPTANCE, COMPLETION, AND ERRORS

A primary or return request uses:
  POST /program-trigger/<program_id>
  Authorization: Bearer <local EtherMotion trigger token>
  JSON body: {"request_id": "<unique event/stage ID>"}

HTTP 202 means accepted, not movement completed. Status is read through:
  GET /program-trigger/<program_id>/status
The demo follows the matching run ID. EtherMotion uses drive command-counter
and stopped checks for command-level completion. An open-loop drive cannot
independently prove shaft position, physical clearance, or successful diversion.

HTTP 409 refuses a command, for example busy/disconnected/not ready. Resolve
alarms, missing zero, disabled trigger gates, busy programs, or lost links
before resuming. A network timeout after POST is uncertain: the command may
already have arrived. Do not resend it with a new event ID. Inspect the run
state in EtherMotion before deciding the next action.

Use Stop + disarm for setup changes. If motion is active or uncertain, inspect
and stop it in EtherMotion as appropriate and establish the mechanism's clear
state before restarting bottle flow. Closing the camera or clearing tracks
does not independently establish physical retraction or stop the belt.

SIMULATOR WORKSPACE (NO PHYSICAL DRIVER)

EtherMotion\UALR-simulator-workspace.json is a schema-version-1 example with
only simulator driver ualr-sim and Once program ualr-sim-reject:
  SIM +12 degrees -> 0.18 second dwell -> SIM -12 degrees.
Those moves illustrate a whole saved cycle. They are not physical rejector
presets. No physical profiles, original workspace state, tokens, or position
checkpoints are included.

Importing a workspace replaces EtherMotion's current workspace. Export anything
you need, stop programs, and disconnect drivers before import. Reconnect only
the simulator for a local test. This document does not import or move anything.

Start EtherMotion Simulator.cmd creates a separate workspace under
data\ethermotion-simulator and opens port 8766, leaving the real workspace on
port 8765 separate. For a live-camera/simulated-actuator trial, set the demo URL
to http://127.0.0.1:8766 and enable the simulator's Ethernet triggers. The demo's
Simulation source itself remains a hardware-free dry run.
